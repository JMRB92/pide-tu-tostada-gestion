# ¡Pide tu tostada! — Gestión v1.01

Candidato de desarrollo para pruebas; NO desplegar para alumnos reales hasta validar las reglas, dispositivos y privacidad. La configuración inicial deja los pedidos cerrados.

## Orden de instalación

1. Instala Node.js 22 y Java compatible con el emulador (JDK 21 recomendado). Abre una terminal en esta carpeta.
2. `npm install` (necesita Internet). `npm test` ejecuta las 15 pruebas puras. `npm run test:rules` ejecuta las 8 pruebas de seguridad en un proyecto de demostración, no en Firebase real. Si alguna falla, no despliegues reglas ni aplicaciones: conserva los resultados para corregirlas.
3. `npx firebase login`. Comprueba el proyecto `pide-tu-tostada` con `npx firebase projects:list`.
4. `npx firebase hosting:sites:create pide-tu-tostada-gestion --project pide-tu-tostada`. Si el ID está ocupado, elige otro único y cambia `hosting.site` en `firebase.json`. No crees otro proyecto Firebase.
5. Solo tras superar el emulador, `npx firebase deploy --only firestore:rules,firestore:indexes --project pide-tu-tostada`. Conserva una copia de las reglas anteriores (denegación total). Nunca uses reglas abiertas de prueba.
6. `npx firebase deploy --only hosting --project pide-tu-tostada` desde esta carpeta. En la URL de gestión entra como Michel con la contraseña que configuraste en Firebase. Inicializa la BD con un código común privado de al menos 10 caracteres. Los pedidos estarán cerrados inicialmente; el catálogo incluye 15 productos. Configura y verifica los alérgenos. El campo de intolerancias permanece apagado hasta autorización.
7. Despliega el ZIP de alumnado (ver su README). Comprueba dominios autorizados de Authentication y verifica en un entorno de ensayo antes de abrir pedidos. Para una prueba integrada usa únicamente nombres ficticios y un código temporal. Las reglas de producción no sustituyen las pruebas del emulador.
8. Configura App Check en las dos apps web, registra reCAPTCHA v3 y añade las claves públicas de sitio en `public/firebase.mjs` de cada repositorio (`APP_CHECK_SITE_KEY`). Despliega, comprueba métricas y aplica enforcement de Firestore después de probar los clientes. No pongas ninguna clave privada en archivos públicos.
9. En GitHub, sube el contenido de esta carpeta, incluyendo `.github/workflows/maintenance.yml` (no node_modules, ni claves). Comprueba que ambos repositorios son privados y que los cargos adicionales de Actions están bloqueados. Para mantenimiento, en IAM de Google Cloud crea una cuenta de servicio exclusiva con el rol Cloud Datastore User (no Owner/Editor); comprueba las políticas de tu organización. Preferiblemente usa credenciales federadas; el workflow incluido admite un JSON de cuenta de servicio mediante secreto `FIREBASE_MAINTENANCE_JSON` en el repositorio de gestión. Nunca lo compartas por chat ni lo subas a GitHub. Si la organización prohíbe crear claves, no fuerces el cambio; habrá que adaptar el workflow a federación. Ejecuta manualmente el workflow solo tras revisar el script. Programa 02:15 UTC (03:15 invierno, 04:15 verano). No se garantiza la puntualidad.
10. Antes de abrir al alumnado: revisa privacidad y derechos de menores, información de alérgenos y precios, verifica login/QR, carga y cuotas; configura código común definitivo. En Configuración activa «Pedidos abiertos según calendario» y aplica ahora. Si hay incidencias, vuelve a cerrar el servicio.

## Reglas y limitaciones

- Firestore Spark: el cliente hace transacciones y las reglas validan marcas, límites, disponibilidad, roles y horas. Las reglas están pendientes de compilación y pruebas en emulador. Los escenarios de traslado de fecha y contadores simultáneos son especialmente importantes por los límites de llamadas documentales de reglas. No autorizar producción hasta que pasen.
- El código común no acredita identidad. El máximo inicial de 3 unidades se calcula por nombre/apellidos normalizados, curso y grupo; no impide suplantación, variantes de nombre o cambios de grupo. Límite técnico 8 unidades por pedido/usuario/día. El administrador puede gestionar pedidos manuales. Los avisos de duplicado exacto consultan los pedidos del dispositivo; no ofrecen una identidad global verificada.
- La contraseña de cada pedido es aleatoria de 128 bits, impresa en PNG privado. El digest SHA-256 es una credencial de acceso, guardada separadamente; no aparece en el QR. No compartas justificantes privados. Una autorización de modificación dura dos minutos y se solicita de nuevo al guardar.
- Dos zonas fijas ESO/CAF con nombres editables; cursos, grupos, catálogo y categorías configurables. Los precios pendientes se leen del catálogo vigente de la fecha, no se sobrescriben todos los pedidos. Las unidades cobradas mantienen su valor. No se sustituye un pedido con cobros; se corrigen las unidades individualmente. El tic se puede reiniciar sin borrar cobros. Estadísticas de solicitudes incluyen pedidos confirmados cancelados; se conserva la última selección válida, no el historial de cambios. Exportación CSV UTF-8 compatible con Excel.
- El QR depende de jsQR/CDN y del navegador; el código escrito es alternativa. PWA usa caché de archivos propios; sin conexión no hay confirmaciones ni entrega segura. No se implementa bloqueo obligatorio de versión mínima ni monitor de cuota automático; se ofrece enlace a uso y caché con actualización normal. No se ha realizado auditoría real de navegador, accesibilidad ni carga. No se ha validado QR escaneable en este entorno.
- El inicio usa la cuenta de acceso proporcionada. Para operación real se recomienda una cuenta exclusiva de cafetería y no compartir una cuenta docente con terceros. La dirección de autenticación aparece en el cliente; no hay contraseña administrativa en el código. GitHub privado no hace privado el JavaScript servido por Hosting.
- No hay lockfile npm generado porque el entorno no tiene Internet. Se fijan versiones directas; comprueba dependencias y genera package-lock.json mediante npm install antes de uso estable. Las dependencias Firebase/QR se cargan desde CDN con versiones fijadas. La autenticación anónima puede conservar cuentas técnicas sin nombres tras borrar pedidos; revisar política de conservación.
- Mantenimiento guarda resumen antes de borrar y reintenta por fecha. El estado local no sustituye la revisión de los registros. La limpieza es diaria de mejor esfuerzo, no una garantía exacta; puede quedar pendiente si se agota cuota, cae la conexión o se pausa Actions. Antes de cerrar festivos con pedidos, se informa del número; la cancelación se reintenta al iniciar el panel y en Actions. No se almacenan datos sanitarios ni contraseñas de alumnos en estadísticas.
